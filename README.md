# Re-implementation of Christopher Strachey's General Purpose Macrogenerator (GPM)

This is just a re-implementation of
[Christopher Strachey](https://en.wikipedia.org/wiki/Christopher_Strachey)'s
[GPM](https://academic.oup.com/comjnl/article/8/3/225/336044), the
[General Purpose Macrogenerator](https://en.wikipedia.org/wiki/General_Purpose_Macrogenerator) in C.

I'm aware of Pat Loughney's [version](https://github.com/psl8/gpm) implemented
in Rust and also
[Martin Richard](https://en.wikipedia.org/wiki/Martin_Richards_(computer_scientist))'s
[version](https://github.com/8l/bcpl) in
[BCPL](https://en.wikipedia.org/wiki/BCPL)
but my searches didn't turn up any versions in C - blame Google, maybe?

So why implement it in C?
=========

I need a macroprocessor - for use in
[romforth](https://github.com/romforth/romforth)

[cpp](https://en.wikipedia.org/wiki/C_preprocessor) is the obvious choice but
it does not support non-alphanumeric macro names.
[M4](https://en.wikipedia.org/wiki/M4_(computer_language)) is the less obvious
option but it seems to have the same limitations as `cpp`. For example, it
cannot use symbols such as `@` or `!` as macro names (I tried, a lot, trust me).
This seems to be a reasonable decision by the GNU M4 authors given how weird M4
already is.

So I needed something more "general" and I hoped that
[GPP](https://logological.org/gpp) would be it, but it has the same limitations
as `cpp` and `m4` with respect to macro names.

In desperation, I'd written a minimal/simple "one-level" macro generator which
is coded in Perl and called m2 (since it is ~ m4/2) - it is currently part of
[romforth](https://github.com/romforth/romforth). While it works for it's
intended purpose, I seem to have reached a point where I need something more
powerful and the next step up seemed to be GPM and since it is so old, I assumed
there had to be plenty of implementations of it, preferably in C.

Now, I want to use C rather than Rust (or anything old like BCPL) to keep the
dependency tree of [romforth](https://github.com/romforth/romforth) from
growing even larger than it already has.

And since I couldn't find an implementation in C, I decided to code it myself.

The original GPM used a symbol that looks like a '$' to start a macro and ';' to
end it. It also uses symbols that are recognizably like '<' and '>' to delimit
the body of a macro and ',' to separate the arguments to the macro.

Martin Richard's BGPM implementation uses '[', ']', '<', '>' and ','
respectively, for each of the symbols from the GPM syntax, to replace the use
of the Flexowriter symbols (used by Strachey) with plain ASCII characters.

My version breaks with both of those traditions and uses '{', '}', '[', ']' (so
that I can toggle on them in vi using the '%' key). I also decided to use the
` `/space character to separate arguments (since it feels more readable).

With that syntax sugar change out of the way, I initially thought of using the
code in BCPL as a template to code the C version but decided midway on a whim
that I really wanted to try to just implement it from scratch by myself. I used
each of the examples from Strachey's paper as a test case and grovelled my way
into an implementation that seems to hold up to a minimal test to generate HTML
as well as a simple test case for the type of use that I envision for romforth.

The implementation for 'Suc' from the GPM paper does not currently work but I
assume the bug is trivial. All the remaining macros listed in the paper (ie
`Successor` etc) are currently untested since the implementation that I
currently have seems to be sufficient for what I need. If anyone out there wants
the full GPM functionality, this is not it - use Pat's version in Rust, maybe?

Code size metrics
==============
Strachey famously said that he implemented GPM (for the Titan/Atlas 2) in 250
"orders" (which roughly translates to "instruction words", I think). Since the
Titan opcodes were 48 bits wide, I assume that weighs in at ~1500 bytes.

Martin Richards has 3 versions of his code in BCPL and since `cloc` does not
grok BCPL, I just used `wc` which reports:
```
  430  1613 10464 bgpm.b
  584  2223 14398 gpm.b
  555  1973 13027 gpmcj.b
```

I was curious to see how C compilers nowadays fare against Strachey's brilliance
at code golf so I counted the bytes generated using the `-Os` option (to
optimize on the size of the code generated by the compiler). It currently
clocks in at ~1215 bytes (but I'm only counting the functions listed in the C
file and not accounting for the code in any of the supporting library functions).

The code itself `cloc`s in at:
```
-------------------------------------------------------------------------------
Language                     files          blank        comment           code
-------------------------------------------------------------------------------
C                                1             25              8            185
```
while `wc` reports:
```
 218  471 3349 gpm.c
```

From eyeballing the CPL code in the appendix to the GPM paper, I think that is
definitely larger than ~200 lines.

My C version was coded over the course of 2 days but I'd spent over a week
before that browsing through the other implementations and papers (as well as
making a couple of false starts).

I also read somewhere that
[Douglas McIlroy](https://en.wikipedia.org/wiki/Douglas_McIlroy)
coded a version of GPM in an afternoon in "just a page" of SNOBOL after
discussions with Strachey. So I tried to see how I would fare coding it in Perl
and came up with a 25 line version (which only partially worked) but I'm sure
it took me much longer than an afternoon (and was not in version control).
